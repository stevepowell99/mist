## gmist: an independent app (formerly a mist fork)

gmist is Causal Map's internal editor for collaborative markdown documents and slides: like Google Docs, but for `.md` files, with files and permissions coming from Google Drive. The aim is that a file edited locally one day and in gmist the next is the same file, equally and seamlessly. Synchronous multi-user editing is not a goal.

It began as a fork of [inanimate-tech/mist](https://github.com/inanimate-tech/mist) (Matt Webb's collaborative markdown editor) but has diverged completely (~160 commits ahead, Drive-only, a new CodeMirror 6 / Y.Text core) and no longer tracks upstream. The mist origin is history only: the `upstream` remote has been removed, there is nothing to merge, and the rest of this file is gmist's own guidance. Treat "based on mist" as irrelevant to current work.

User-facing copy was renamed to gmist on 17 June 2026 (the single `APP_NAME` constant in `app/shared/constants.ts` drives the wordmark and tab titles; a few prose strings and the Obsidian review banner say gmist too). The structural identifiers stay `mist` on purpose: the worker name (`mist` in `wrangler.jsonc`, which fixes the live URL `mist.broad-smoke-cc64.workers.dev`) and the `mist:` document frontmatter key. Renaming the worker would break every existing shared secret link; renaming the frontmatter key would orphan saved comment threads. **Drive conflict-safety and GitHub removal (16 June 2026):**

- **Guiding principle (decided 18 June 2026): content is the source of truth; a Drive `headRevisionId` is only a hint and a timestamp is decoration.** Every sync boundary must decide "did it change?" by comparing the body (`stripFrontmatter`), never by a revision id or `modifiedTime` equality. The only id/time uses left are the conditional-write token (backstopped by a content recheck) and one safe shortcut (equal id ⇒ unchanged); `modifiedTime` is display-only. Do not reintroduce version- or time-based "newer" logic. And do NOT propose making gmist Drive-API-only to dodge the multi-writer churn: the whole point of choosing Drive is that the file is also a real local/Obsidian file (the "edit locally one day, in gmist the next" promise), so API-only would mean Drive buys nothing over R2/D1. The multi-writer setup (gmist API + Drive for Desktop) is acceptable precisely because reconciliation is content-based; the residual revision churn self-heals (see the false-conflict recovery below).
- GitHub is gone entirely: import, commit-back, `GitHubBackend`, the `github.ts`/`github.server.ts` modules, the `gh/import` route, `GITHUB_TOKEN` and `ADMIN_KEY` are all removed. Drive is the only backend, and the `DocBackend` abstraction now has one real implementation.
- Auto-save is ON (debounced ~2.5s) and conflict-safe. The relay never silently overwrites the editor. The decision is content-based, not time-based: Drive's `headRevisionId` cannot order revisions, and a re-upload stamps a new id on old content, so timestamps cannot be trusted. In `agents/document.ts` `checkUpstream`: on every connect it re-reads Drive and, when nothing is unsaved here and Drive's body differs, ADOPTS Drive (Drive is the source of truth on a clean reopen); unsaved edits and Drive diverged keeps the editor, forks the incoming Drive copy to a `… (drive copy …)` sibling, and saves yours to the main file; an explicit reload first snapshots the editor to a `… (gmist unsaved …)` sibling, so it can never lose work.
- **The comparison is BODY-only (18 June 2026 fix).** The editor's `Y.Text` body is frontmatter-stripped (threads live in a Yjs map), but a save runs `serializeThreads`, which YAML-reformats the whole frontmatter and re-adds the `mist:` block whenever the doc has comments. So a saved file always differs from the editor text in the frontmatter even when the body is untouched. `checkUpstream` therefore compares `stripFrontmatter(local)` vs `stripFrontmatter(base)`/`stripFrontmatter(drive)`: the body is the real "did it change" signal. Comparing whole files (the old bug) made every external edit look like a local edit, so it forked the change aside instead of adopting it (the stray "drive copy" siblings). Adopt re-seeds the editor as `serializeThreads(driveBody, [], driveFrontmatter)` so the `mist:` YAML never leaks into the body.
- **False-conflict recovery on save (18 June 2026).** The conditional write compares Drive's `headRevisionId` to the version we last saw; a mismatch throws "changed upstream". But Drive for Desktop re-uploads our own save and stamps a NEW revision id on identical content, so with nobody editing the next save was falsely rejected and auto-save latched into "conflict". Now on that error `doCommit` re-reads Drive and compares the BODY against our last save (`lastCommitMd`): if equal it is our own content re-stamped (a re-upload churn), so it re-anchors to the new version and writes the pending content (one retry); only a genuine body divergence stays a conflict. Logged as `save … (recovered from a re-upload churn)` vs `save-conflict`.
- **No spurious "drive copy" fork on a churn reconnect (23 June 2026).** `checkUpstream` (runs on every connect) forks the incoming Drive version to a `… (drive copy …)` sibling when the editor has unsaved edits AND Drive's body differs. It was missing the churn check `doCommit` already has: when Drive's body equals our OWN last save (`lastCommitMd`) but carries a new `headRevisionId` (Drive for Desktop re-uploaded our content), that is not an independent edit, so the editor's unsaved edits sit on the same baseline and there is no third version to preserve. It now re-anchors to the new revision and keeps editing (logged `churn-reanchored`) instead of forking. Forking only happens for an independent THIRD version (Drive differs from both the editor and our last save). This was the source of the repeated identical sibling files (`drive copy 1649`, `1720`, …) appearing on every reconnect during an active Drive-for-Desktop churn.
- **Conflict self-heals, it does not latch (23 June 2026).** The re-upload-churn recovery above only fires when, at save time, Drive's body already equals our last save. But Drive for Desktop often pushes a stale local copy a beat AFTER our save lands, so the recheck sees a different body, declares `save-conflict`, and pauses auto-save; the churn then self-heals on Drive's side a few seconds later but nothing re-attempted the write, so sync stayed stuck (the "Conflict" badge was a dead-end span with no escape). Fix is client-side in `DocumentContext`: while `conflict` is set, re-attempt `saveNow` on a widening backoff (`CONFLICT_RETRY_BASE_MS` × attempt, `CONFLICT_RETRY_LIMIT` tries). The relay's recovery only rewrites once Drive has converged back to our content, so a transient churn clears itself and emits `committed` (which clears `conflict` and cancels the retry loop) with no sibling clutter; a real external edit keeps diverging and stays conflicted after the cap. The `SaveStatus` "Conflict" badge is now a button → `reloadFromDrive` (snapshots unsaved edits to a recovery sibling, then adopts Drive) so a real edit also has a one-click escape. This is the client retry counterpart to the server-side single-retry recovery; it does NOT touch the parked save/dirty machinery's representation.
- **No phantom "Saving" on open (18 June 2026 fix).** The unsaved badge must baseline against the editor's OWN serialization, never the relay's stored file bytes. For a commented doc the two never match: the editor body has no `mist:` block (threads in a Yjs map), `serializeThreads` re-emits and YAML-reformats the frontmatter, threads serialize in document-position order while the file stores another order, and `useTextThreads` can auto-create thread metadata with fresh ids/timestamps on load. So the old "authoritative committed hash on connect" (`quickHash(lastCommitMd)`) was structurally unequal to the client's `currentHash`, writing one save on every open. Now `DocumentContext` baselines `lastCommittedHash` to its own `currentHash` and keeps re-baselining through the post-sync settle (body, `threads` map and legacy `meta` map land on separate ticks), then FREEZES on the user's first real edit. Crucially the `unsaved` badge is also GATED on a `userEdited` flag, so a freshly loaded file reads "Synced" with no flash even before the baseline settles (a load is in sync by definition; only an actual edit can make it unsaved). A real edit is a CodeMirror `userEvent` transaction (not a remote Yjs sync update; `CodeMirrorEditor` `onUserEdit`) plus the comment/reply/resolve/delete actions (`markUserEdited` sets the ref the effect reads and the state the badge reads). The agent sends NO connect-time `committed`; it only confirms a hash after an actual save (`doCommit`), which matches because the relay writes exactly the client's pending serialization.
- **Diagnostic sync trail (18 June 2026).** The agent records each sync decision (`open`, `adopt-drive`, `conflict-fork`, `save`, `save-conflict`, `upstream-error`) into a `sync_log` SQLite table (pruned to the last 200), exposed via the agent's `?synclog` GET. The `/drive/docinfo` route returns that log plus richer Drive metadata (modified time, owner, last editor, size, link) for the open file, and the Drive sidebar (`FolderSidebar`) shows a file-details block with a collapsible "Sync activity" trail. First stop when sync looks wrong.
- Root cause it guards against: a file in a folder that Google Drive for Desktop syncs has TWO writers, the relay through the Drive API and Drive for Desktop pushing the laptop's local copy. When the local copy is stale and Desktop pushes it, it overwrites the relay's newer content under a fresh revision id. Keep one live writer per file where you can: do not edit a gmist file in the app while Drive for Desktop is live-syncing that same file on a machine.

**Slides grammar / theming simplification (19 June 2026). A theme is now just variables.** Two follow-on simplifications, both about "one truth, not two":
- **One mechanism for the slide canvas.** The deck canvas (`.reveal-viewport` / `.reveal` background+text) is set ONCE in the deck shell (`PREVIEW_CSS` in `slides-build.ts`) from `--slide-bg` / `--ink`. A theme NO LONGER restates those; it only sets the variables (`--slide-bg`, `--ink`, `--accent`, `--accent-2`, optional `--divider-bg`, a `font-family` on the `:is(.reveal,.preview)` block) plus its accent/component overrides. To restyle a DOCUMENT preview too, a theme adds a `.preview { background; color }` line (causal-map deliberately omits it, so an un-themed doc keeps its serif look). `causal-map.css`'s header is the reference for writing a theme.
- **One mechanism for colouring a whole slide = reveal's full-viewport background.** A divider (lone `#`) or `.title-page` slide with no background of its own gets `data-background-color: var(--divider-bg, var(--slide-bg))` emitted by `parseHeading`, so the colour fills the slide AND the letterbox, seamless. - **Friendly aliases compose standard classes.** `CLASS_ALIAS` in `slides-build.ts` expands a friendly name to a bundle of standard utility classes at parse time, so it carries no bespoke CSS and every axis utility overrides it (the normal cascade). `.caption-bar` (and back-compat `.shot-cap`) = `.bg-ink .left-0 .right-0 .bottom-0 .footer`. Add new sugar there, not as new CSS.

**Split-view cursor/slide sync (17 June 2026).** In split view the editor and the deck preview track each other in both directions, and the editor is the higher-priority side. **Local-fs mode: gmist over this machine's own files, no Drive (17 July 2026).** For solo work on your own files, `npm run dev:local` runs gmist against the local filesystem: no Google secrets, no sign-in, no internet, and the Drive-for-Desktop double-writer churn disappears (gmist edits the same physical file Desktop watches, like Obsidian does). Set `LOCAL_FS_URL` and `LOCAL_FS_TOKEN` in `.dev.vars` (see `.dev.vars.example`); production never sets them, so the deployed worker is Drive-only by construction. How it fits together:
- **There is no root and no search.** Local mode is not scoped to a folder: a file is reached by its absolute path, so files on any drive (C:, G:, H:) work. It has NO name/full-text search either, because walking the machine would be pointless when TagFox already indexes it. TagFox's "Open in gmist" row button is the way in: it opens `http://localhost:5173/open?path=<absolute path>` when a local gmist is up (see TagFox's `CLAUDE.md`). The in-app quick-open palette (`/go`, Ctrl/Cmd+Alt+J) still BROWSES folders but shows "search is off in local mode" for a typed query (`drive.search.ts` returns a `searchUnavailable` flag, `QuickOpen.tsx` renders it).
- **The storage seam is `app/lib/google.server.ts`, now a facade, not an implementation.** It re-exports `drive-common.ts` (types + pure ACL/id helpers) and dispatches every call to `google-drive.server.ts` (the previous Drive code, unchanged) or `google-localfs.server.ts`. Every call site in the app, and the agent, imports the facade only, so nothing else knows which backend is live. Adding a storage operation means adding it to both implementations: the `StorageOps` type in the facade is the compile-time guard that they stay in step.
- **The mode is decided once, in `getDriveAccessToken`, and travels in the token.** A local "access token" packs the sidecar URL and the shared secret (`localfs:<secret>@<url>`); `impl(token)` picks the backend from it. So dispatch is per-call and explicit, with no ambient state. Do NOT reintroduce a hostname sniff or a module-level mode flag: an env var is the switch, and a machine that has not opted in cannot accidentally be in local mode.
- **The Worker cannot read the disk, so a sidecar does, and the token is its whole access control.** `scripts/localfs-server.mjs` is a loopback HTTP server (workerd has no filesystem); `npm run dev:local` starts it and the dev server together, dying together. It reads and writes any file the user can, so the loopback bind is NOT the protection: any web page you visit can POST to `127.0.0.1` (no-CORS, DNS-rebinding defeats origin checks). Every request must carry `LOCAL_FS_TOKEN`, and any request bearing a browser `Origin` is refused outright. "You start it yourself" does not help: the attacker is a page in your browser talking to your running sidecar, not a rogue process. The token is not something the user manages: `dev:local` generates one into `.dev.vars` on first run (both the sidecar and the worker read it from there; the worker does not see `process.env`, which is why it is written to the file, not passed ephemerally). There is deliberately no path allowlist (it would not stop that attack and would trap gmist under one drive letter). The sidecar owns ALL path arithmetic (Windows path semantics in one place with node's `path`); the worker holds only opaque ids and never splits a path.
- **Ids are absolute paths, versions are content hashes.** A local file's id is `lf_` + base64url(absolute path) (`app/lib/localfs-ids.ts`), so it spans drives and decodes for debugging. The version token is a content hash, which is the project's "content is the source of truth" rule made literal: re-saving identical bytes keeps the version, so the conflict machinery only fires on a real change. It is unchanged and still works (an external edit while the room is closed adopts on reopen, verified). Deck-relative assets (`../_shared/x.css`) resolve through the sidecar's `/resolve-rel`, verified rendering a real deck.
- **Deliberate local-mode differences:** sign-in is bypassed (`getRequestEmail` returns a fixed local identity, since the files are the local user's own) and permissions are a constant anyone/writer grant, so share links are meaningless in local mode; `/trash` moves into a `.gmist-trash` beside the file rather than deleting; rename changes a file's path and therefore its id, so a room open on the old name stops resolving until reopened.

**Known limitations / deferred simplifications (19 June 2026).**
- **Each open mints a NEW room.** `/drive/import` uses a random `generateDocumentId()`, so opening the same Drive file twice (e.g. Ctrl/Cmd-click a Drive-sidebar result for a new tab) makes two rooms both bound to that one file. Accepted for now; making import deterministic per `fileId` (reuse the room) is a deferred, larger change.
- **The save/dirty machinery is the next DRY target (PARKED, 19 June 2026).** Its state is spread across `DocumentContext` (`currentHash`, `lastCommittedHash`, `userEdited`, `conflict`, `upstreamChanged`, `forkedNotice`) and `agents/document.ts`; it works and now carries a state-machine comment, but it is the place most likely to grow another "one truth, two representations" bug. The agreed direction, if it ever earns the churn: hash the CRDT (the `Y.Text` body + a canonical threads-map digest, byte-identical on client and agent by construction) as the dirty signal instead of comparing two `serializeThreads` outputs, which removes the serialization-drift root cause; optionally model the client side as one explicit state enum rather than several booleans. DECISION: this sounds right but it is working fine now, so it is PARKED, not scheduled. Revisit only deliberately (integration tests first), not as a drive-by; do not start it without a reason.

**The Y.Text body must be LF-only. CRLF corrupts the editor (19 June 2026, critical invariant).** CodeMirror 6 represents its document with `\n` only: `EditorState.create({doc})` silently drops `\r` (a 24-char CRLF string becomes a 22-char doc). The Y.Text CRDT, however, stored the file verbatim, so a CRLF file (any Windows/Obsidian-saved `.md`) desynced every editor position after a line break: typing at a word-end wrote the character mid-word into the CRDT, and the preview/reload then showed it mid-word. Deterministic on CRLF files, perfect on LF. Fix: canonicalise CRLF/CR -> LF at every point content enters gmist, `driveRead` (every Drive read, so the seed, the upstream comparison and adopt all agree on `\n`), the agent seed (`document.ts`, for uploads/demo that skip `driveRead`), and `replaceBodyFromText` (adopt backstop). A CRLF file converts to LF on its first save (standard, harmless). Do NOT reintroduce verbatim CRLF into the Y.Text. This was misdiagnosed for a long time (blamed on cache, then a Drive-for-Desktop adopt race) until a direct CodeMirror test named it; the real cause was line endings, not sync.

**Quick-open launcher + headless client (19 June 2026).** A Spotlight palette (`app/components/QuickOpen.tsx`) opens Drive markdown by name: kind filters, folder-context navigation, parent-folder match ranking (server `parents=1` in `drive.search.ts`), inline Google sign-in. The bare `/go` route (`app/routes/go.tsx`) is the launcher surface an OS hotkey opens; in-app overlay is Ctrl/Cmd+Alt+J. Steve's AHK (`stevekeys.ahk`, NOT in this repo) binds Ctrl+Alt+K to open `/go` as a Chrome **app window** in stable Chrome's Default profile (where his gmist sign-in and the installed PWA live; his daily browser is stable Chrome 149, with a separate unused Chrome Beta install). A headless Yjs peer, `scripts/gmist-bot.mjs`, joins a doc's live session over the agent WebSocket (same protocol as the browser) to read it and post CriticMarkup; auth is a `mist_session` cookie from `$GMIST_SESSION` or the gitignored `scripts/.gmist-session`. Driven by the `gmist-review` project skill (`.claude/skills/gmist-review/`; `.claude/skills/` is un-ignored so project skills are version-controlled).

**Direct open-by-id deep-link (`GET /open?file=<id>`, 23 June 2026).** For external tools that already hold a Drive file id (not a name): `/open?file=<driveFileId or Drive URL>` imports the file and redirects straight into the room, gated by the signed-in browser session. The import core is shared with `POST /drive/import` via `importDriveFileToRoom` in `app/lib/drive-import.server.ts` (do not re-inline the import in either route). Like `/drive/import` it mints a NEW room per call (see the note above). First consumer: the TagFox "Open in gmist" row button, which reads the Drive id off the local mirror and opens this URL.

**Editor selection toolbar (19 June 2026).** Selecting text in the editor shows a floating toolbar (`app/lib/cm-selection-toolbar.ts`): Comment, Delete, Replace, Insert. The suggest actions work in EDIT mode too (the differentiator over Docs/Word), because CriticMarkup is literal `Y.Text`, so wrapping a range as `{-- --}`/`{++ ++}` is a normal edit, not a separate track-changes mode. Comment reuses the sidebar input via a `mist-comment` window event. Shared by docs and decks (one editor). The comments panel collapses to a navbar hamburger (far right) plus an invisible right-edge hover-peek (no visible strip); selecting Comment with the panel closed peeks it open and closes it after save.

**Review panel is a real edit list, and CriticMarkup rendering is one shared module (14 July 2026).** `app/lib/critic.ts` (`criticSpans` + `renderCriticHtml` + `stripCritic`) is now the single grammar Preview and the deck build both call; `cm-criticmarkup.ts` keeps only the CodeMirror decorations. Root cause of the earlier "substitution shows as literal `{~~old~>new~~}`" bug: neither renderer handled substitutions, so `marked` read the `~~` as GFM strikethrough and left the braces and `~>` behind. The RHS panel now lists every suggestion (`EDITS (n)`) as its own card, Insert/Delete/Replace with the removed/added diff and its own Accept/Reject, instead of four ungrouped buttons; a `{>>...<<}` comment adjacent to a suggestion (a space either side still counts) is paired and shown on the card, and Accept/Reject resolves the paired comment and jumps the cursor to the next edit. Clicking a card or comment scrolls the editor to its markup; the card/thread under the cursor self-highlights and scrolls into view in the sidebar (guarded to only re-evaluate on actual cursor movement, so picking a resolved thread isn't immediately undone).

**Scroll sync: one coordinate (the source character offset) and one anchor per BLOCK (14 July 2026, critical invariant).** All three panes (editor, preview, comments) are kept in step through the source character offset, because it is the only measure that is exact everywhere. `lineBlockAt` only measures lines CodeMirror has actually rendered; anything outside the viewport gets an *estimated* height (a wrapped paragraph counts as one line), so mapping editor pixels straight to preview pixels overshot by thousands of px below the fold, and this was misdiagnosed twice before a Playwright drift harness (`_tmp/drift.py`, gitignored) pinned it down. Pixels are read only where they are real: the fully laid-out preview, the editor's own viewport top (`posAtCoords`), and, for the reverse direction, CodeMirror's own `scrollIntoView`. Do not reintroduce a pixel-based CodeMirror measurement for content below the viewport.
- The offset-to-pixel map comes from anchors the preview emits itself: `insertPosAnchors` (`app/lib/source-anchors.ts`) puts a hidden `<br data-pos="N">` before every top-level block before the render pipeline runs, so the DOM carries one anchor per paragraph, list, table, quote, fence and heading. Heading-only anchors (the first version) were far too coarse: between two headings the position was interpolated by character fraction, and a section holding an image, a table or a code block is tall on the page and short in characters, which is what left the panes hundreds of px apart mid-section. Measured after the change on a mixed document: 0px at every block, both directions. `<br>` is the marker tag because it is void (an unclosed `<span>` would nest the rest of the document inside it) and a lone open tag on its own line is a block-level HTML block, so it never joins the paragraph after it. A marker must never interrupt a paragraph, and a list must stay one block (a marker between two items ends the list and starts a new one) — both are handled in the scanner and covered by tests.
- The comments pane is the third panel: each card carries `data-pos` (a suggestion's `from`, a thread's `position`) and `syncAside` in `docs.$id` scrolls the list so the cards for the top of the page are at the top of the list. It FOLLOWS and never drives, deliberately: a comment must not be able to yank the document about. Clicking a card still jumps the editor, which is the reverse direction, done on purpose.
- Also fixed on the way: a `#` inside a fenced code block was counted as a heading, which desynced the heading counts between editor and preview and silently dropped the whole sync to the (bad) proportional fallback; fenced code is now skipped when counting headings (`extractOutlineFromText`).

**`Preview` must never pass a fresh object to `dangerouslySetInnerHTML` (14 July 2026, critical invariant).** React compares that prop by reference, so a new `{ __html: html }` literal on every render — even when `html` itself hasn't changed — re-sets the DOM node's innerHTML and wipes out anything injected into it afterwards. Symptom: a mermaid diagram renders once, then reverts to a plain code block on the next keystroke, cursor move or save-status tick, because the effect that draws it is keyed on `html` and never re-fires. Fix: memoise the object so the DOM is only rewritten when `html` actually changes; mermaid also caches each rendered SVG by source and re-applies it in the same frame. This applies to anything else ever injected into the preview DOM post-render, not just mermaid — don't reintroduce a raw `{ __html: ... }` literal there.

**A view-wide class on the editor goes through `EditorView.editorAttributes`, never `view.dom.classList` (13 August 2026, critical invariant).** CodeMirror composes the editor's `class` attribute itself and rewrites it wholesale whenever its own attributes change, which taking focus does, so a class added by hand is dropped on the first click. Live preview lost its typography that way while its decorations carried on hiding the marks, which read as the document collapsing back to source view; clean view had carried the same fault unnoticed. Both now ride in one compartment in `CodeMirrorEditor.tsx` (`attrsCompRef`). The live preview layer itself is `app/lib/cm-live-preview.ts`, the fourth View (Ctrl/Cmd+Alt+4); design and build notes in `plans/live-preview.md`.

**Mermaid is bundled, not CDN-loaded, and detected by fence content, not the `language-mermaid` class (14 July 2026).** Diagrams were fetched from jsdelivr at render time; a blocked or slow CDN load silently left every fenced mermaid block as literal source text, and some rendering path was also stripping the `language-mermaid` class before it reached the app. Mermaid is now bundled into the app, and detection checks whether a fenced block's first line starts with a mermaid keyword (`%%{`, `flowchart`, `graph`, `sequenceDiagram`, etc.), class or no class — this also covers the Quarto fence form ` ```{mermaid} `. Each diagram renders independently so one bad one can't blank the rest.

**Image embed fixes (14 July 2026).** Two bugs, not a delivery/CDN issue: a path containing spaces must be written `![alt](<path with spaces>)`, and the rewriter demanded a space-free src, so any image path with spaces (e.g. under a `... -- ...` folder name) never reached the Drive proxy and 404ed against the app origin. Separately, Obsidian's own `![[img/x.jpg]]` embed syntax was rendered by nothing — it fell through to the wikilink converter and came out as plain text. Since Obsidian writes an embed's path from the vault root rather than the note's own folder, `drive/asset` now retries the lookup from up to three parent folders.

### Local dev gotchas

- `npm run dev` serves at `http://localhost:5173`. On a cold Vite cache, the first open of a fresh room can fail to sync ("Outdated Optimize Dep" / a dynamic-import error) because the editor route lazy-loads CodeMirror/Yjs and Vite re-optimises mid-navigation. Hard-reload or open the doc a second time; deployed builds are unaffected.
- **Localhost is for occasional testing only, never for real work.** Real editing always happens on the deployed worker (the source of truth; see "Always deploy to remote after changes" above), so a file is the same whether opened locally elsewhere or in gmist. `npm run dev` runs the Worker AND the Durable Objects in workerd on this machine, so a test run consumes none of the account's DO duration (the free-tier limit that nearly tripped on 15 June 2026); that is a side benefit of testing locally, not a reason to do work there. Secrets come from `.dev.vars` (gitignored; template in `.dev.vars.example`): the `GOOGLE_*` values must match production (Cloudflare secrets are write-only, so reuse the originals), and `SESSION_SECRET` can be any local random string. For Google sign-in to work on localhost, add `http://localhost:5173` to the sign-in OAuth web client's Authorized JavaScript origins in the Google Cloud console. Collaboration is localhost-only; sharing links with others needs the deployed site.
- Scratch work goes in `_tmp/` (gitignored locally); Playwright here is the Python package, not the npm one.
- **A backgrounded `npm run deploy` can exit 0 without actually shipping (hit 14 July 2026).** A deploy run in the background silently wrote nothing while still reporting success, so a subsequent live-worker test was against stale code and the reported fix looked like it hadn't landed. If a fix doesn't show up live after deploying, verify the bundle itself (e.g. grep the fetched deployed JS for the new code) before assuming the fix is wrong — don't trust the exit code alone.
- **The editor is the CodeMirror 6 / Y.Text core (#13).** The CRDT is a single `Y.Text` of raw markdown (`doc.getText("body")`), bound to CodeMirror via `y-codemirror.next`; save is `ytext.toString()`, an identity. ## Project Overview

gmist is a collaborative markdown and slides editor for Google Drive files, like Google Docs but for `.md`/`.qmd`. A file is shared by a secret link; collaborators sign in only to pass the file's Drive ACL and can edit or suggest (CriticMarkup). Live awareness (multiplayer presence) is supported; simultaneous multi-user editing is not a goal. Drive is the single source of truth; edits auto-save back to the file (conflict-safe, see the 16 June note above).

## Tech Stack

- **Backend:** Cloudflare Workers + Durable Objects (SQLite storage)
- **Frontend:** React Router 7 (SSR) + Cloudflare Agents SDK
- **Editor:** CodeMirror 6 + Y.Text (CRDT, via `y-codemirror.next`)
- **Styling:** Tailwind CSS 4
- **Language:** TypeScript (strict mode)
- **Testing:** Vitest with v8 coverage

## Architecture

See `docs/technical-architecture.md` for full details.

### Directory Layout

- `agents/` — Server-side Durable Object agents (currently just `DocumentAgent`)
- `app/components/` — React UI components
- `app/lib/` — Editor logic, CriticMarkup, Yjs provider, utilities
- `app/shared/` — Constants and types shared between client and server
- `app/routes/` — File-based routing (`home.tsx`, `docs.$id.tsx`, `new.ts`)
- `workers/app.ts` — Cloudflare Worker entry point
- `tests/` — Unit tests (`tests/unit/`) and integration tests (`tests/integration/`)

### Import Path Alias

`~` resolves to `app/` (configured in tsconfig and vitest). Use `~/lib/foo` instead of relative paths.

### Critical Rule: Server/Client Separation

Client-side React components must **never** import from `agents/`. The `agents` package uses `cloudflare:` protocol imports that don't exist in the browser. Use `app/shared/` for types needed by both sides.

### Real-Time Collaboration Flow

The multiplayer system works as follows:

1. **`DocumentAgent`** (`agents/document.ts`) — a Durable Object that holds a Yjs `Y.Doc` in memory, persists state to SQLite on every update, and relays Yjs sync/awareness messages between connected WebSocket clients.
2. **`yjs-provider.ts`** (`app/lib/`) — client-side WebSocket provider that connects to the agent at `/agents/document-agent/:docId` and handles Yjs sync protocol encoding/decoding.
3. **CodeMirror 6** binds to the Yjs `Y.Text` body (`doc.getText("body")`) through `y-codemirror.next`, which also renders remote cursors from the awareness protocol.
4. **Worker entry** (`workers/app.ts`) — `routeAgentRequest()` intercepts `/agents/:agent/:name` requests before React Router handles the rest.

### CriticMarkup / Suggest Mode

Track-changes is plain CriticMarkup delimiter TEXT in the single `Y.Text` body, styled by CodeMirror decorations, not a mark or node model. The canonical description is the CodeMirror 6 / Y.Text core bullet under "Local dev gotchas" above, with design notes in `plans/ytext-core.md`. Key files:

- `app/lib/cm-criticmarkup.ts`: decorations that style the `{++ ++}`/`{-- --}`/`{== ==}`/`{>> <<}` delimiters
- `app/lib/cm-suggest.ts`: suggest mode, rewriting edits into CriticMarkup additions and deletions
- `app/lib/cm-comments.ts` and `app/lib/useTextThreads.ts`: comments matched to the Yjs `threads` map by content
- `app/lib/critic-parser.ts`: parses CriticMarkup syntax into clean text and ranges

### Testing Constraints

- The `agents` package uses `cloudflare:` imports — it **cannot** be imported in plain Vitest. Test agent logic through integration tests or mock the imports. Unit tests should focus on pure logic in `app/lib/` and `app/shared/`.
- Coverage thresholds ramp linearly from 0% to 80% between Feb–Dec 2026 (see `vitest.config.ts`).
- Tests live in `tests/unit/` and `tests/integration/`, mirroring the source structure.

### ESLint Conventions

- Unused variables must be prefixed with `_` (e.g., `_args`, `_ctx`).
- Tagged template expressions are allowed (for `this.sql` in Durable Objects).
